1. Product Overview
DDdesk.ai is a multi-tenant SaaS platform for study libraries, reading rooms, self-study centres and similar education spaces. Each library operates as an isolated tenant while using the same central platform.
Each approved library receives a unique subdomain such as gyan.dddesk.ai.
Library data, students, seats, fees, attendance, staff and reports remain tenant-isolated.
Library owners get a simple operational dashboard rather than a technically complex ERP-style interface.
Students receive a web/mobile experience for attendance, seat, membership, fees, payments, notices, stories and complaints.
The platform supports offline cash/UPI workflows as well as online payments.
Advanced analytics and AI operate only on data the current user is authorized to access.
2. Product Goals
Make daily library operations simple enough for non-technical owners.
Digitize student, seat, attendance and fee management.
Support real Rajasthan-style credit/pending-fee practices without losing accounting visibility.
Give every library a professional public website.
Reduce manual follow-up through reminders and notifications.
Provide owners with actionable business insights instead of only raw reports.
Create a scalable architecture for multi-library and multi-branch operations.

4. Global Functional Rules
Every tenant-owned record must contain a Library/Tenant reference.
Every protected API must verify both authentication and tenant authorization.
Deleted business records should preferably use soft-delete/archive where historical reporting is required.
Money values must use a consistent currency configuration; default currency is INR (₹).
Date/time handling must use the library's configured timezone, with India timezone as the default.
Important financial, permission, membership and configuration actions must create audit records.
Owner-configurable rules must not silently override explicit owner decisions.
User-facing lists should support search, filtering, pagination and appropriate empty states.
Exports must support the complete filtered dataset, not only the currently visible page.

38. Acceptance Criteria
Each tenant can operate independently without seeing another tenant's records.
Owner can complete student admission, seat assignment, membership and payment/credit flow end-to-end.
Owner can collect partial and pending fees and see accurate outstanding balances.
Attendance updates reflect correctly in student and owner views.
Website content published by a library appears only on that library's public website.
Student can access only their own profile, membership, attendance and financial information.
Reports reconcile with source records.
Online payments are marked paid only after verified confirmation.
Critical actions are permission-protected and audited.
System can recover from common errors without corrupting financial or membership data.

Appendix A — Key End-to-End Business Flows
A.1 Library Onboarding
Registration → Admin Review → Approval → Subdomain Provisioning → Owner Login → Profile Setup → Seat Setup → Plans → Website Publish → Student Acquisition.
A.2 Student Admission
Website/Walk-in Enquiry → Follow-up → Student Creation → Plan Selection → Seat Assignment → Payment or Credit → Membership Activation → Student Login.
A.3 Monthly Fee with Credit
Monthly charge created → Paid/Partial/Credit → Due date tracked → Reminder → Owner-configured grace period → Payment allocation → Receipt → Membership status updated.
A.4 Renewal
Expiry alert → Student chooses renewal → Plan selected → Payment/credit → New membership period → Seat retained or reassigned according to policy.
A.5 Complaint
Student complaint → Staff assignment → In Progress → Resolution → Student update → Close → Report/analytics.
